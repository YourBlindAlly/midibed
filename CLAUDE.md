# MidiBed (placeholder name) - looping MIDI drone / pad / percussion generator for iOS

"MidiBed" is a PLACEHOLDER name, chosen so Rusty isn't pressed to pick a real one yet. Everything
(display name, bundle id, module/class prefix) uses `midibed`/`MidiBed` so a later rename is one
pass. Sideload-only, so bundle id changes are cheap right now (unlike LyriCue's).

## What it is
An iOS app that generates MIDI only and sends it to other apps (AUM, Synth One, Moog apps, hardware).
It does not need to contain a real synth, but ships a tiny built-in test synth so it can be heard
with no routing. Goal: the always-looping bed (drone/bass, pad chords, percussion) for Rusty's live
chillout folktronica, mostly instrumental. Rusty plays live on top.

Design decisions already agreed with Rusty (2026-10-07):
- Own use first, sideloaded (no App Store), so background-audio mode is fine.
- Patterns are generated by RULES and tweaked in-app (not hand-entered step grids):
  Euclidean (hits/steps/rotation) per drum voice, each voice with its own loop length (polymeter),
  swing, per-step probability, ghost-note velocity variation, fills every N bars.
- Drone/bass: held notes + "CC wanderers" (slow random-walk/LFO on any CC number, range, speed,
  smoothness) + occasional probabilistic note events (fifth in/out, octave drops, slow root changes).
- Pad chords (phase 3): looping progressions, voice-led voicings, per-note probability/velocity drift.
- Scenes: stored sets of patterns/chords/CC settings; switch at loop/bar boundary. Later: Bluetooth
  page-turn pedal to switch scenes/mute drums/fill.
- Clock: internal tempo + tap tempo; optionally send/follow MIDI clock.
- Built-in backup sound: tiny AVAudioEngine synth (2 detuned saws -> lowpass -> envelope for
  drone/pads; sine kick; noise hats/snare). Must respond to the same CCs (cutoff/resonance) so
  wanderers are audible with no routing. Needs a "MIDI only" switch so it doesn't double the real synth.
- Rusty already owns: AudioKit Synth One, several Moog iOS apps, AUM (probably), Audiobus (probably).
  A CoreMIDI virtual source shows up in AUM directly; Audiobus isn't required.
- Other platforms later maybe (Android android.media.midi, Windows via loopMIDI, Mac same CoreMIDI).
  Keep pattern/scheduling logic separable from CoreMIDI output.

Architecture rules:
- The clock/scheduler/pattern engine lives in NATIVE Swift, using CoreMIDI packet timestamps and
  scheduling slightly ahead. NEVER schedule musical timing from JS timers. JS only sends parameter
  changes and receives state.
- UI: Expo / React Native. VoiceOver-first (see "Accessibility" below).
- Phases: (1) Swift module: virtual MIDI source + look-ahead scheduler + one drone w/ two CC
  wanderers + one Euclidean drum voice + built-in test synth, minimal UI. (2) multi-voice drums,
  polymeter, swing, probability, scene storage. (3) pad chord layer, pedal scene switching, MIDI
  clock. (4) later: AUv3, other platforms.

## Accessibility (VoiceOver-first) - lessons carried over from LyriCue
- One-finger swipes belong to VoiceOver; don't rely on custom swipe gestures. Use plain buttons
  (double-tap) and `accessibilityRole="adjustable"` + increment/decrement for value controls
  (put those props on a `View`, not a `Text`). Use Custom Actions for rows with secondary actions.
- Small tap targets need generous `hitSlop`; wrap in `SafeAreaProvider`/`SafeAreaView` so header
  items stay clear of the status bar.
- Frequently changing text that may hold focus needs a FIXED accessibilityLabel, not one tracking
  its content (else VoiceOver re-announces on every change).
- Don't let the app's own speech race VoiceOver announcements; gate any spoken output behind a
  user action. (This app mostly makes MIDI; keep spoken feedback minimal and optional.)
- Double-tapping a labeled iOS button re-speaks its label; for repeated actions prefer an
  adjustable element.
- React Navigation v7: `navigate()` pushes duplicates; use `popTo()` to return to an existing screen.
- Persisted data: when adding a field to a saved shape, write a `migrateX()` that fills defaults at
  load, since Release builds crash silently on missing fields.
- Native event listeners: centralize behind one JS bus that calls the native `addListener` once;
  effects subscribing to native events use an empty dependency array and read the callback via ref.
- Pedal reference (for phase 3): LyriCue's `modules/cueme-pedal-input` uses a native
  first-responder view with `pressesBegan/pressesEnded` because `GCKeyboard.keyChangedHandler`
  delivered no events for his pedal; `GCKeyboard` is still used for connect/disconnect (debounce
  disconnect ~1.5 s). A text field stealing first responder silently stops presses; call a
  `reclaimPedalFocus` (dispatched async to the next run loop) when returning to the screen.
